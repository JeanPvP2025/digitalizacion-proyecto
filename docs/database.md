# Base de datos NODRIA

La base se organiza como un comercio español con catálogo público, cuentas de cliente y operaciones de venta. El esquema vive en `supabase/migrations/`; `supabase/seed.sql` contiene datos ficticios para desarrollo local. La configuración de Supabase mantiene `public` como esquema del Data API y concede acceso por tabla de forma explícita.

## Contratos para la aplicación

- `products.id` es `text` para conservar los IDs del catálogo de demostración (`pr_fluxbook14`, `pr_foundry_s`, `pr_loom27`, `pr_linkmesh`, `pr_slateair`, `pr_arcssd`). Las categorías se consultan con `product_categories` y `categories`.
- Los precios y variantes viven en `product_variants`: `current_price` y `compare_at_price` se muestran con IVA incluido; `tax_rate` sirve para separar el importe neto e IVA en el pedido. `inventory` contiene unidades por almacén; `anon` no lo lee y `authenticated` solo puede leerlo con rol de logística. No hay API pública de stock exacto.
- El checkout llama `public.place_order(p_cart_id, p_idempotency_key, p_shipping_address, p_billing_address)` con sesión autenticada. El RPC toma precios actuales, comprueba publicación y existencias, bloquea carrito/variantes/stock, reserva inventario por almacén, crea `orders`, snapshots en `order_items`, un intento `payment_transactions` pendiente y un evento `order_events`, y convierte el carrito en una transacción. Repetir la misma clave para el usuario devuelve el pedido existente. `shipping_total` y `discount_total` comienzan en cero; no se aceptan precios ni descuentos del navegador.
- Clientes solo leen sus pedidos, líneas, pagos y eventos. Las escrituras directas de `orders`, `order_items`, `payment_transactions`, `inventory`, `warehouses`, `inventory_reservations` y `order_events` están revocadas para roles de cliente, personal y `service_role`; las transiciones usan RPC. La clave `service_role` permanece únicamente en servidor.
- `public.resolve_demo_payment(p_order_id, p_outcome, p_event_id)` está disponible solo para `service_role`. Acepta `approved` o `failed`, requiere un ID estable de evento y es idempotente por ese ID. Aprobado cambia pago y pedido a `paid` y conserva la reserva. Fallido marca el pago `failed`, cancela el pedido y libera todas sus reservas en la misma transacción. Una reserva pendiente no expira sola: el servidor debe resolver explícitamente el resultado. Es un contrato de simulación académica, no verifica ni procesa pagos reales.
- `public.fulfill_order(p_order_id)` consume las reservas de un pedido pagado, reduce `on_hand` y `reserved`, escribe movimientos de stock y cambia el pedido a `shipped`. `public.mark_order_delivered(p_order_id)` solo permite pasar de `shipped` a `delivered` y guarda `delivered_at`. Ambos RPC requieren `service_role`; el servidor debe ejecutarlos y nunca enviar esa clave al navegador.
- `public.adjust_inventory(p_warehouse_id, p_variant_id, p_delta, p_reason)` es la única operación de recepción/ajuste manual y requiere `service_role`. Rechaza deltas que consuman unidades ya reservadas. `inventory_movements` conserva el delta, saldo resultante, motivo, actor y referencia al pedido; las filas son append-only. Las FK compuestas aseguran que cada reserva y movimiento se refiera al mismo SKU y almacén.
- `public.request_return(p_order_id, p_reason, p_items)` acepta un array de líneas `{order_item_id, quantity, condition_note?}` y requiere la sesión del cliente. Bloquea el pedido para serializar solicitudes concurrentes, admite solicitudes durante los 30 días posteriores a `delivered_at` y rechaza cualquier suma que exceda las unidades compradas. Los estados distintos de `rejected` siguen ocupando cantidad. Las transiciones permitidas son `requested → approved → received → refunded → closed`, `requested → rejected`, y cierre desde `approved` o `received`. La creación directa de `return_requests`/`return_items` está revocada.
- Los presupuestos autenticados se guardan en `quotes` y `quote_items`. Antes de crear una cuenta, el formulario B2B puede insertar en `quote_inquiries`, limitado a nombre, email, teléfono, empresa, mensaje y consentimiento. Una policy permite solo la inserción con consentimiento; solo ventas puede consultar y actualizar esas solicitudes.
- Atención al cliente usa `support_tickets` y `support_messages`. El cliente crea tickets abiertos de prioridad normal, asociados opcionalmente a su organización o a un pedido propio. Puede leer sus mensajes públicos y añadir mensajes no internos. Los roles `support_agent` y `super_admin` gestionan tickets y notas internas.

## Identidad y permisos

Cada alta en Supabase Auth crea o sincroniza una fila en `profiles`. El trigger copia el email de Auth y el nombre inicial; el usuario solo puede cambiar `display_name`, `phone` y `locale`. Los roles internos se administran en `user_role_grants`, que no admite escritura desde la API del cliente. Roles disponibles: `catalog_manager`, `fulfillment_manager`, `support_agent`, `sales_manager` y `super_admin`.

Las organizaciones usan `organizations` y `organization_memberships`. `public.create_organization(p_slug, p_legal_name, p_display_name, p_tax_id, p_billing_email)` crea la empresa y su primer miembro `owner` atómicamente; un índice único impide más de un owner. Los administradores de una organización y `super_admin` pueden añadir o quitar miembros `buyer`/`viewer`, con `added_by = auth.uid()`; el rol `sales_manager` no puede asignar ni quitar membresías globales. No se puede crear ni borrar otro `owner`/`admin` desde el Data API. No hay invitaciones ni promoción de miembros a administrador en este contrato. No se seedearon usuarios, perfiles ni contraseñas de Auth: crea una cuenta en Auth y asigna roles internos por una vía administrativa confiable para probar flujos de personal.

Las tablas del esquema `public` tienen RLS habilitado. Las funciones `SECURITY DEFINER` viven en el esquema no expuesto `private`, fijan `search_path` vacío y validan usuario/estado según contrato. Los wrappers públicos usan `SECURITY INVOKER` y sus privilegios `EXECUTE` se conceden solo a `authenticated` o `service_role` según la operación. El registro `audit_events` es append-only para clientes; los triggers guardan actor, entidad y nombres de columnas modificadas, sin copiar valores de PII.

Las inserciones anónimas/autenticadas en `crm_leads` solo reciben permisos por columnas (`contact_name`, `email`, `phone`, `company`, `message`, `consent_to_contact`). `source`, `submitted_by` y `created_at` quedan bajo defaults/controles del servidor. Personal de ventas puede leer las solicitudes; no puede editar directamente esos campos.

## Datos de demostración

El catálogo seed coincide con los seis productos del fixture de storefront, sus SKUs, precios, ratings y cantidades iniciales. Incluye seis categorías, especificaciones, un almacén de Madrid y contactos ficticios bajo el dominio reservado `.example`. Los contactos seed no son cuentas Auth y no permiten iniciar sesión. El seed conserva las filas de inventario si ya existen; úsalo en entornos locales/de demostración, no para cargar stock de producción.

## Operación local

Con Supabase CLI y Docker disponibles, `pnpm dlx supabase@latest start` inicia el stack local; `pnpm dlx supabase@latest db reset` reconstruye el esquema desde las migraciones y ejecuta `supabase/seed.sql`. El proyecto reserva los puertos 56200–56209 porque Windows excluye el rango predeterminado.

Las pruebas PostgreSQL/pgTAP versionadas en `tests/database/` se ejecutan con `pnpm dlx supabase@latest test db --local tests/database`. El reset, seed, las pruebas y `pnpm dlx supabase@latest db lint --local` forman el gate de cambios de esquema. La suite contiene 60 verificaciones de permisos, contratos RPC, conciliación de reservas, cierres de pago/fulfillment, idempotencia y límites de devolución. Las funciones de pago y operaciones no tienen consumidores en la UI/API todavía; el owner de Auth/runtime debe integrarlas desde handlers de servidor antes de presentar esos flujos como conectados.

## Límites pendientes de integración

- `public.place_order` todavía devuelve el pedido existente cuando se repite una clave del mismo usuario, sin comparar carrito ni direcciones; el adaptador de checkout debe generar y retener una clave por intento y la migración futura debe rechazar reutilizarla con otro payload.
- `place_order` todavía valida que ambas direcciones sean objetos JSON, no que tengan los campos mínimos de preparación. Definir y validar ese contrato sigue pendiente.
- Fuera de esta unidad quedan el contrato de volumen B2B (`DI-01`), intake atómico de soporte (`DI-06`), condiciones de publicación/ciclos de categoría y aserciones del seed (`DI-09`), snapshots de presupuestos (`DI-10`), auditoría de otros dominios (`DI-07`) y autorización del centro de operaciones demo (`F-01`). Revisar sus informes antes de marcar el producto completo.
